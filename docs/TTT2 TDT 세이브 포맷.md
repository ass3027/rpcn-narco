# TTT2 TDT 세이브 포맷

Sep 23, 2026 · @Someone

Tekken Tag Tournament 2(`NPWR02973_00`)는 한 계정의 온라인 전적 전체를 **3,420바이트 TUS 슬롯 하나**에 담아 둔다. 대전이 끝나거나 온라인 메뉴를 드나들 때마다 차분이 아니라 통째로 다시 올린다. PS3 빅엔디안이고, 맨 앞 4바이트가 CRC-32 체크섬이다.

체크섬은 **풀렸다**. 표준 CRC-32(IEEE 802.3)인데 버퍼를 읽는 바이트 순서가 교과서와 반대라 `zlib.crc32` 계열 전수 대입에서 다 빗나간다. 오프셋·타입·의미는 아래에 표로 정리했고, 각 항목에 확신도를 붙였다.

기계판은 ImHex 패턴 파일 `ttt2_tdt.hexpat` 이다. 이 문서는 그걸 사람이 읽는 형태로 옮긴 것이다.

## 근거 자료와 표기

RPCN 운영 서버의 세이브 **57,715개 / 263명**이 원본이다. 파일명은 `data_id`이고 발급 순서라, 서버 로그의 `TusSetData`(npid 포함)와 시각순으로 1:1 정렬해 저장자를 특정했다. DB 교차 검증점 251/251 일치.

그 상태에서 같은 유저의 연속 저장을 diff 해 전이를 뽑았다. 아래 수치는 전부 그 전이 통계다.

연결 방법은 두 번 바뀜었다. 처음에는 `battle_score` 증분을 가정해 이었는데 승 6,083 / 패 13,629로 나왔다. 같은 서버 안의 대전이니 승과 패는 같아야 하므로 가정이 틀린 것이었다. 가정을 빼고 \*\*"캐릭터별 전적 합계는 한 판에 0, 1, 2만 늘어난다"\*\*는 성질만으로 다시 이었다.

|  | 가정 기반 | 성질 기반 |
| --- | --- | --- |
| 연결된 전이 | 49,976 (86.6%) | **57,321 (99.3%)** |
| 승 / 패 | 6,083 / 13,629 | **13,451 / 13,626** |
| 비율 | 0.446 | **0.987** |

오른쪽 열의 승패 균형이 복원이 편향되지 않았다는 근거다. 이 검증 없이 얻은 수치는 신뢰하면 안 된다.

### 확신도 표기

| 표기 | 의미 |
| --- | --- |
| **\[확정\]** | 전이 통계에 반례가 없거나 외부 자료(게임 실측 / DB)와 일치 |
| **\[추정\]** | 관측된 거동에는 부합하나 게임 내 용도까지 특정 못함 |
| **\[미상\]** | 값은 있으나 의미 불명 |

⚠️ **"전 표본에서 0"은 그 바이트가 쓰이지 않는다는 뜻이 아니다.** 관측된 플레이 범위에서 0이었다는 뜻일 뿐이다. 표본에 없는 모드(토너먼트, 팀전 등)에서 채워질 수 있다.

## 전체 레이아웃

| 영역 | 범위 | 크기 | 내용 |
| --- | --- | --- | --- |
| Header | `0x000`–`0x06F` | 112 B | 체크섬, 시각, 계정 계급, 누적 지표 |
| Characters | `0x070`–`0xB7F` | 59 × 48 B | 캐릭터별 계급과 전적 |
| Tail | `0xB80`–`0xD5B` | 476 B | 진행 중인 대전 상태, 계정 총계 |

캐릭터 ID가 `i`면 레코드 시작은 `0x70 + i * 0x30`이다. ID와 레코드 위치의 대응은 \*\*\[확정\]\*\*이고, 이름표는 다르다(아래 별도 절).

저장의 **52%는 전적이 전혀 변하지 않는 재업로드**다. 변화를 기대하고 파싱하면 안 된다.

### 이 파일로 해보는 검산

- `total_matches` 1,082 = `total_wins` 600 + `total_losses` 482 → 미분류 **0**
- 캐릭터 승 합계 1,200 ÷ 계정 총승 600 = **정확히 2.0** → 항상 태그로 뛰었다
- `match_pending` 0 이므로 결과 저장이고, 그래서 `own_character_1/2`가 0으로 지워져 있다. 이걸 "Paul로 뛰었다"고 읽으면 틀린다
- `own_rank` 18 vs `opponent_rank` 17 → 비슷한 상대와 매칭됐다

## Character record — 48 B × 59

시작 오프셋 = `0x70 + i * 0x30`. 아래는 레코드 내 상대 오프셋이다.

| 상대 | 타입 | 이름 | 확신도 | 내용 |
| --- | --- | --- | --- | --- |
| `+0x00` | u8 | **rank** | 확정 | 캐릭터 계급. 관측 0–35. 계정 계급과 달리 **강등이 실제로 일어난다** |
| `+0x01` | u8 | unknown\_01 | 미상 | 단일 승패 전이 53,553건에서 변화 0. 패딩 가능성 있음 |
| `+0x02` | u16 | **rank\_points** | 확정 | 계급 진행 점수. 관측 0–21,499. 계급 안의 게이지다 |
| `+0x04` | s8 | rank\_streak | 확정 | **부호 있는** 연승/연패, 관측 −23–39. `0xFF`는 255가 아니라 −1 |
| `+0x05` | u8\[2\] | zero\_05 | 미상 | 전 표본 0 |
| `+0x07` | u8 | unknown\_07 | 미상 | `+0x01`과 같이 단일 승패 중 고정 |
| `+0x08` | u32 | wins | 확정 | 이 캐릭터 누적 승수 |
| `+0x0C` | u32 | losses | 확정 | 이 캐릭터 누적 패수 |
| `+0x10` | u8\[0x20\] | reserved\_zero | 미상 | 전 표본 0 |

`rank_streak` 갱신 규칙은 승리 시 `max(old, 0) + 1`, 패배 시 `min(old, 0) - 1`이고 실제 변화 19,847건이 전부 일치한다. **매 판 한 캐릭터만 갱신된다** — 2명 이상 갱신 0건, 아무도 갱신 안 됨 7,029건.

`wins`/`losses`는 서로 독립이다. 계정이 한 판 졌을 때 59캐릭터의 `wins`는 전부 변화 0이고, 그 반대도 마찬가지다.

| `0xC4B` | u8 | opponent\_rank\_2 | 추정 | 상대 두 번째 캐릭터 계급 |
| `0xC4C` | u32 | zero\_c4c | 미상 | 전 표본 0 |
| `0xC50` | u32 | incomplete\_history | 추정 | 하위 30비트 = 최근 30회 미완료/비정상 종료 이력. **승패 이력이 아니다** |
| `0xC54` | u8 | match\_pending\_mirror | 확정 | `0xC44`의 복제. 57,272/57,272 동일 |
| `0xCD8` | u32 | marker\_cd8 | 미상 | 항상 `0x00000100` |
| `0xCDC` | u32 | **total\_wins** | 확정 | 계정 누적 승수. +1 전이 13,353건이 전부 `total_matches` +1과 동시 |
| `0xCE0` | u32 | **total\_losses** | 확정 | 계정 누적 패수. +1 전이 13,523건 |

나머지 구간(`0xB88`–`0xBAF`, `0xBB4`–`0xBDF`, `0xBE4`–`0xC0F`, `0xC14`–`0xC3F`, `0xC55`–`0xCD7`, `0xCE4`–`0xD5B`)은 전 표본에서 0이다.

`incomplete_history` 갱신 규칙은 대전 시작 시 `H = ((H << 1) | 1) & 0x3FFFFFFF`(26,508/26,508 일치), 정상 종료 시 `H &= ~1`이다. 고의 종료와 통신 오류는 구분되지 않는다.

## 계급 체계

`rank_points`는 절대 점수가 아니라 **한 계급 안의 게이지**다. 계급마다 상한이 있고, 서로 겹친다.

- 승 **+2000** / 패 **−2000** (2단 이상에서 승 9,262건 · 패 9,399건이 정확히 이 값)
- 상한 초과 → 승급, 0 미만 → 강등
- **계급 진입 시 게이지는 중간에서 시작한다** — 이게 승급과 강등의 문턱을 비대칭으로 만든다

| 계급 | 상한 | 진입(승급) | 진입(강등) | 승급까지 순승 | 강등까지 순패 |
| --- | --- | --- | --- | --- | --- |
| 11 | 11,999 | 8,100 | 7,300 | 1.9 | 4.0 |
| 13 | 12,999 | 8,651 | 7,400 | 2.2 | 4.1 |
| 16 | 15,999 | 8,999 | 6,714 | 3.5 | 4.2 |
| 17 | 18,999 | 13,060 | 11,001 | 3.0 | 6.1 |
| 21 | 16,999 | 11,000 | 8,999 | 3.0 | 5.1 |
| 25 | 20,999 | 13,000 | 10,439 | 4.0 | 6.4 |
| 29 | 20,999 | 12,674 | 9,799 | — | 5.7 |

### 강등

세 가지가 예외 없이 지켜졌다.

1. **패배로만** 일어난다 — 강등 유발 전이 1,386건이 전부 패배, 승리로 강등 0건
2. 폭은 **언제나 정확히 1계급**
3. 강등 직전 점수의 **77%가 2,000 이하** — 게이지가 바닥에 닿아서 떨어진다

패배 한 판당 강등 확률은 계급별 4–12%다.

**계급 10(1단)은 바닥이다.** 그 계급에서의 패배 2,639건 중 강등 0건이고, 패배의 66%가 0점이다.

### 급 계급 0–9는 별개 체계

절대 사다리다. 계급 `r`의 점수가 `200 × r` 근처에 고정되고 구간끼리 겹치지 않는다. 1승 = +200이고 그 자리에서 바로 승급, 패배는 +50이며 강등은 없다.

### 티어 경계

진입 지점이 이웃보다 놓은 계급이 티어 시작이다 — **17(1.72×), 21(1.53×), 25(1.68×), 29(1.45×)**. 그 직전 계급(16·20·24·28)은 승급 상한이 높아 티어 진입을 막는다.

⚠️ **계급 13은 이 신호가 없다**(1.04×). 11·12·14·15와 구분되지 않으므로 티어 경계인지는 데이터로 뒷받침되지 않는다.

⚠️ 승급 시 `rank_points` 리셋 폭이 계급마다 제각각이다 — 10→11은 **+6,000**, 11→12는 **0**, 17→18은 **−10,000**. 규칙은 \[미상\].

## 저장 동작

### 대전은 두 번 저장된다

| 단계 | 일어나는 일 |
| --- | --- |
| 대전 시작 | `match_pending` = 1, `own_character_1/2`와 계급 스냅샷 기록, `incomplete_history = ((H << 1) \| 1) & 0x3FFFFFFF` |
| 결과 저장 | 승패 카운터 증가, `match_pending` = 0, `own_character_1/2`를 0으로 지움, `incomplete_history &= ~1` |

따라서 **결과 파일만 보고 `own_character_*`를 "직전 출전 캐릭터"로 읽으면 틀린다.** 비활성 상태의 ID 0을 Paul 선택으로 읽어서도 안 된다.

시작 저장의 `{0xC46, 0xC47}` 집합은 다음 결과에서 전적이 증가한 캐릭터 집합과 **26,868/26,876 = 99.97%** 일치한다.

### 태그와 단독 출전

태그는 두 캐릭터의 승(또는 패)이 각각 +1 되고, 단독은 한 명만 오른다. 그래서 `sum(캐릭터 승) / 계정 총승`은 1.0–2.0 사이가 된다.

- 유저 196명 전원이 이 범위 안 (범위 밖 0명, 모순 0명)
- 정확히 2.0 = 85.7% (항상 태그)
- 단일 승리 13,353건 중 합계 +2가 13,266건, +1이 87건

유저별 단독 출전 판수 = `2 × 총승 − sum(캐릭터 승)`. 전체의 약 \*\*0.8%\*\*만 단독이다.

⚠️ 따라서 **"캐릭터 합계는 정확히 2배"라는 제약을 강제하면 안 된다.**

## 체크섬 해제 — `0x00`

다항식은 **표준 CRC-32(IEEE 802.3)** 인데, 버퍼를 읽는 바이트 순서가 교과서와 반대다 — **byte 0이 최하위 차수**. 그래서 `zlib.crc32` 계열 전수 대입이 전부 빗나간다.

### 계산법 — 구현용

```python
import zlib

def checksum(buf: bytes) -> int:
    # init=0, xorout=0 의 raw CRC-32
    crc = zlib.crc32(buf[4:] + b"\x00" * 4760, 0)
    return crc

# 파일 맨 앞에 BE32 로 저장
```

표준 CRC-32 테이블을 그대로 쓰되 **입력을 `file[4:]` + 영 바이트 4,760개**로 주면 된다. `payload_size`(3,400)와는 무관하다.

### 계산법 — 대수적 형태

```text
P = 0x1DB710641      # CRC-32 IEEE 0x104C11DB7 의 33비트 역순
C = 0x85840EC7
V = Σ byte[o] · x^(8o)   for o in [0x04, EOF)   (mod P)
checksum = C · x^32 · V
```

두 방식은 **완전히 동일**하다(300/300 교차 확인).

### 복원 경로

1. 연속 저장 쌍 **57,010건**으로 GF(2) 연립을 세워 비트별 임펄스 `E[bit]`를 구했다. 미지수 3,156 / rank 2,322 / 모순 0 / 홀드아웃 7,768건 100% 적중.
2. 후진 대입까지 마친 임펄스 2,202개에서 규칙이 드러났다.
   - 바이트 내: `E(o, k+1) = E(o, k) · x` — 1,809/1,809 (100%)
   - 바이트 간: `E(o+1, k) = E(o, k) · x^8` — 683/683 (100%)
   - → `E(o,k) = C · x^(8o+k)`, 법을 역산하니 `0x1DB710641`
3. 전 파일 재현 **57,709/57,715 (99.99%)**.

⚠️ 불일치 6건은 알고리즘 문제가 아니다. 내용과 저장값이 모두 같은 **한 세이브의 복사본**이고, 그 파일 자체가 자기 내용과 맞지 않는 체크섬을 갖고 있다 (`data_id` 193150, 207902, 207903, 207906, 207907, 207908).

### `rank_streak` 가설

"내 팀 최고 계급(동률이면 첫 캐릭터)이 10 이상이고 상대 최고 계급과 차이 1 이내"가 **53,539/53,553**에 맞으나 예외 14건이 남는다.

### 표본의 한계

관측된 최고 계급은 **35**다(캐릭터·계정 모두). 36–42에 도달한 사례가 표본에 없으므로 그 구간의 거동은 전부 미지수다. 계급 27 이상은 승급 표본이 15건 미만이라 수치 신뢰도가 낮다.

## 서버 적용과 위험

RPCN은 세이브를 `tus_data/{data_id}.tdt`로 보관하고, DB의 `tus_data` 행이 현재 `data_id`를 가리킨다. `TusGetData`는 그 파일을 **그대로 바이트로 넘기며 내용을 해석하거나 검증하지 않는다.** 즉 DB가 가리키는 파일을 덮어쓰면 게임이 다음 로그인 때 그걸 받는다. DB는 건드릴 필요가 없다.

| 위험 | 내용 |
| --- | --- |
| 1 | 게임이 체크섬 외에 추가 검증을 하는지 **미검증**이다 |
| 2 | 해당 계정으로 접속해 저장이 일어나면 새 `data_id`가 발급되어 덮어쓴 파일은 버려진다. **오프라인일 때 교체할 것** |
| 3 | 운영 서버다. 반드시 전용 테스트 계정으로만, 교체 전 원본 백업. 실제 유저 세이브는 **복구 수단이 없다** |

⚠️ 클라이언트는 세션 동안 자기 사본을 들고 있다가 매 대전마다 다시 올린다. 서버 로그 기준 `TusGetData` 3,916회에 `TusSetData` 18,270회, 플레이어당 한 번 받아간 뒤 **평균 19.8회 연속 저장**한다. 따라서 접속 중인 계정의 파일을 고쳐도 클라이언트가 몰라서 다음 저장에 되돌린다.
